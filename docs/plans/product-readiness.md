# Forma product readiness implementation plan

Status: in progress. Requested October 11, 2026.

Owner: root orchestrator. Implementation: Luna agents with bounded file ownership. Baseline: commit `2821a1a`, 42 passing tests and passing production build. Review evidence: `/workspace/forma-review/forma-product-readiness-review.md`.

## Goal and constraints

Deliver a predictable, complete professional diagram workflow: create → refine → apply identity → save → agent revision → reopen → export. Preserve local-first operation, stable IDs, portable versioned native documents, and the shared engine. Existing files must retain their appearance and human intent unless the user deliberately changes it.

No publishing, deployment, external accounts, telemetry, or live customer-data mutations are required. New local code, migrations, tests, docs, and reversible fixtures are authorized. Live OAuth/storage/deployment checks will be reported as external qualification when credentials/deployments are unavailable, not claimed as verified.

## Execution and review protocol

- Agents read only the relevant review sections and owned files. Send the root a short architecture/API checkpoint when other workstreams depend on the decision.
- Work in the shared repository without commits, resets, stashes, broad formatting, or overwriting another agent's changes. Format only owned files. Do not spawn nested agents.
- Ask the root for cross-scope edits or architectural blockers. Send a message when a dependency is ready, a blocker needs a decision, or the bounded assignment is complete. Avoid routine progress chatter.
- Each handoff includes changed files, behavior before/after, focused validation, remaining risks, and integration instructions.
- Root inspects actual diffs and behavior, requests corrections, then runs combined tests/build/schema/format and browser journeys. Passing agent checks alone do not mean accepted.
- Root waits for agent messages between checkpoints. Periodic checks are for direction or overdue blockers, not continual polling.

## Wave 2 — Workspace, identity and accessibility

Start bounded assignments when their Wave 1 dependencies are accepted.

- W1: document-scoped draft recovery, multiple-tab coordination, clear save states, hosted account isolation and sign-out cleanup. Choose browser or server recovery deliberately; never restore another account's content.
- W2: complete library lifecycle across browser/local/hosted adapters: rename/move, duplicate, trash/restore, folders/recent items, human-friendly creation, conflict comparison and save-as-copy. Revision and ownership checks apply to every mutation.
- W3: typed design-system evolution: token references and validation, node/edge/group defaults, compatible roles/component presets, light/dark modes, durable hosted library, clone/delete, preview and explicit revision upgrades. Keep embedded portable snapshots and old systems readable.
- W4: usability/accessibility: readable contrast/type, larger interaction targets, keyboard connection/path/resize/group actions, focus restoration/trapping, mixed-value controls, snapping guides, lock/hide, error boundary and native-document recovery/export. Preserve the current visual identity rather than redesigning unrelated UI.
- W5: complete shape palette and registry: triangle, hexagon, parallelogram, trapezoid, document, cloud, circle/square aspect constraints; shared text-safe regions, boundary/ports/rendering/resize/inspection. Do not accept schema fields that have no behavior.
- W6: agent preview/diff/apply with expected revisions, structured field errors, changes summary, shared commands and regression coverage for unrelated human intent.

## Wave 3 — Output, qualification and release hygiene

- Q1: useful export options: selection/content, transparent background, scale/page dimensions; PDF and one editable interchange exporter (draw.io) using the scene/native semantics. Validate exported files and document editability/font limits.
- Q2: domain completeness where supported: native ER cardinality markers, swimlane/container conventions, sequence/lifeline and calibrated timeline capability designs with fixtures. Implement incrementally; label unsupported domain semantics honestly until verified.
- Q3: automated browser journeys in CI for create/edit/reset/route/system/save/reload/agent-roundtrip/export, with focused accessibility checks. Cover cancellation, malformed imports, errors, dense graphs, negative pins and multiple tabs.
- Q4: workload matrix and performance report: first usable canvas, ordinary gesture latency, recomposition, memory and export. Proposed targets: p95 ordinary gesture <100 ms; ordinary recomposition <1 s; larger supported work cancellable without blocking UI. Choose supported graph sizes based on results.
- Q5: hosting operations: storage-aware readiness, structured content-free diagnostics, quota/conflict signals, backup/restore and migration/rollback runbooks, independent-runtime revocation/offboarding verification. Real Google/TLS/provider tests require an accessible deployment.
- Q6: installation/package clean-room checks, schema generation parity, backwards-compatible example gallery, fonts/browser/CLI output checks, current publishing documentation, support/limits page and release notes. Do not publish or deploy as part of this task.

## Release gates

1. Every native property has intentional editable/advanced/derived/read-only classification; everyday edits support effective display, edit and reset across UI/CLI/MCP.
2. Cosmetic edits preserve presentation/geometry and unrelated intent; no-op gestures do not create document history.
3. Repeated move/resize/reconnect preserves route mode, attachment and bounded intent; canvas/export geometry agrees.
4. Simultaneous saves and library mutations never silently overwrite; drafts and conflicts have recovery; restore drill succeeds.
5. Ownership/scopes/expiry/revocation hold across independent runtimes; live provider checks explicitly distinguished from synthetic tests.
6. Measured supported workloads meet responsiveness budgets or expose bounded cancellable progress.
7. Keyboard users can complete creation/editing/export; contrast/focus/zoom checks pass; manual screen-reader/touch checks documented.
8. Clean install/upgrade and documented export formats work; unsupported fonts/scripts/domain features have clear boundaries.
9. Combined tests/build/schema/format/browser journeys pass after integration; root has inspected critical diffs and retained evidence.
